enable_mfabooleanEnable MFA simulation for this landing page
mfa_sms_profile_idintegerID of the SMS profile to use for sending verification codes
mfa_fromstringOverride sender ID for MFA SMS (optional, uses profile default if empty)
mfa_messagestringSMS message template. Use {{.Code}} for the code. Default: "Your verification code is: {{.Code}}"

Database Encryption

AnglerPhish supports AES-256-GCM encryption for sensitive database fields including SMTP passwords, SMS provider credentials, IMAP passwords, and captured event details (credentials submitted by phishing targets).

Note: Encryption is optional and backward compatible. The application works without an encryption key, and encrypted/plaintext data can coexist.

Environment Variable

Variable Description
ANGLERPHISH_ENCRYPTION_KEYBase64url-encoded 32-byte (44 character) encryption key for AES-256-GCM. If not set, encryption can still be turned on for the current session from Settings → Encryption.

Managing Encryption in the UI

Administrators (users with the Modify System permission) manage encryption from Settings → Encryption. The tab is not shown to other users, and no restart is needed to turn encryption on. The old command-line flags have been removed.

State Meaning
OffNo key is loaded and no encrypted values exist. Data is stored in plaintext.
OnA key is loaded, either from the ANGLERPHISH_ENCRYPTION_KEY environment variable or for this session only (generated in the UI or unlocked by pasting it). A session key is lost when the process exits, so a warning banner is shown on every admin page until the key is added to the environment or your secret manager.
LockedEncrypted values exist but the key is missing (missing_key), does not match the stored check value (wrong_key), or is malformed (invalid_key). Anglerphish stays up, a red banner is shown to admins (other users see a generic notice), and sending with a still-encrypted SMTP, SMS or IMAP credential is refused with encryption key unavailable. Data written while locked is stored in plaintext until you run Encrypt existing data.
DisablingDecryption is in progress or incomplete. The key stays loaded for reads, new writes are no longer encrypted, and you can retry until no encrypted values remain.

Actions

  • Generate key — creates a new key and shows it once. Save it, then paste it back to confirm you have a copy. Encryption turns on immediately for new writes, using the key for this session. Existing data is not migrated automatically.
  • Preview / Encrypt existing data — the preview reports what would change without modifying anything; encrypting then converts existing plaintext values. Run this after turning encryption on, and after any period spent locked.
  • Preview decryption / Disable encryption — decrypts all stored values and, once none remain encrypted, unloads the key. Afterwards remove the key from your environment or secret manager; if it is still set at the next restart, encryption turns back on.
  • Unlock — paste the key while locked. Failed attempts are rate limited (5 failures per user within 15 minutes).
  • Discard encrypted data — available only while locked, for when the key is permanently lost. Permanently clears the encrypted values after you type DISCARD ENCRYPTED DATA. If ANGLERPHISH_ENCRYPTION_KEY is still set afterwards, remove it — or keep it knowingly: at the next restart it is accepted as the new encryption key.

A malformed ANGLERPHISH_ENCRYPTION_KEY no longer aborts startup. If encrypted data exists, Anglerphish starts in the Locked state (invalid_key) so it can be fixed from the UI; otherwise it starts with encryption Off and logs a startup warning.

In split deployments (--mode admin and --mode phish running as separate processes) a session key exists only in the process where it was entered. Use the ANGLERPHISH_ENCRYPTION_KEY environment key for split deployments.

Encryption API

All endpoints are under /api/encryption/, require an admin (Modify System) and return 403 for other users. Other HTTP methods return 405 and malformed JSON returns 400. The key is never logged and appears only in the generate response, which is sent with Cache-Control: no-store.

Endpoint Request body Description
GET /api/encryption/status—Returns state (off, on, locked, disabling), source (none, environment, session), locked_reason, startup_warning, per-field counts in report, plaintext_count and migration_running.
POST /api/encryption/generate—Returns {"key": "..."}. The key is not loaded.
POST /api/encryption/enable{"key": "..."}Loads the key for this session and turns encryption on. 400 for an invalid key; 409 if encryption is already on or encrypted data exists.
POST /api/encryption/unlock{"key": "..."}Unlocks with the correct key. 400 for a wrong or invalid key, 409 if not locked, 429 after 5 failed attempts in 15 minutes.
POST /api/encryption/migrate{"direction": "encrypt" or "decrypt", "dry_run": true or false}Encrypts or decrypts stored values, or previews with dry_run. Returns results and status. 400 for an invalid direction; 409 if a migration is already running, no key is loaded, or encrypt is requested while disabling.
POST /api/encryption/disable—Decrypts all values and turns encryption off. 409 if decryption is incomplete (retry).
POST /api/encryption/discard{"confirmation": "DISCARD ENCRYPTED DATA"}Locked state only. Permanently clears encrypted values. 400 for a wrong confirmation, 409 if not locked.

Production Deployment

ANGLERPHISH_ENCRYPTION_KEY remains the long-term home of the key. Keep it out of config.json, the database and the application folder, and inject it from your secret store. Replace the example paths and names with your own.

systemd with an environment file (restricted permissions): [Show Example]

sudo mkdir -p /etc/anglerphish
echo "ANGLERPHISH_ENCRYPTION_KEY=your-key" | sudo tee /etc/anglerphish/secrets.env
sudo chmod 600 /etc/anglerphish/secrets.env
sudo chown root:root /etc/anglerphish/secrets.env

# /etc/systemd/system/anglerphish.service
[Service]
EnvironmentFile=/etc/anglerphish/secrets.env
ExecStart=/opt/anglerphish/anglerphish

systemd LoadCredential (the key is exposed as a file, so a small wrapper exports it): [Show Example]

# /etc/systemd/system/anglerphish.service
[Service]
LoadCredential=encryption_key:/etc/anglerphish/encryption_key
ExecStart=/bin/sh -c 'ANGLERPHISH_ENCRYPTION_KEY="$$(cat "%d/encryption_key")" exec /opt/anglerphish/anglerphish'

Docker secrets (the secret is mounted under /run/secrets/): [Show Example]

# docker-compose.yml
services:
  anglerphish:
    image: your-anglerphish-image
    secrets:
      - anglerphish_encryption_key
    entrypoint: ["/bin/sh", "-c", "ANGLERPHISH_ENCRYPTION_KEY=\"$$(cat /run/secrets/anglerphish_encryption_key)\" exec ./anglerphish"]

secrets:
  anglerphish_encryption_key:
    file: ./anglerphish_encryption_key.txt

Vault Agent: render the key into an environment file with a template, then load it with EnvironmentFile= as above: [Show Example]

# vault-agent.hcl
template {
  contents    = "ANGLERPHISH_ENCRYPTION_KEY={{ with secret \"secret/data/anglerphish\" }}{{ .Data.data.encryption_key }}{{ end }}\n"
  destination = "/etc/anglerphish/secrets.env"
  perms       = "0600"
}
Important: Never lose your encryption key! If lost, encrypted passwords become unrecoverable and you'll need to re-enter all credentials.

Admin SSO (OIDC)

Anglerphish supports optional OIDC login for the admin UI, compatible with any standard OpenID Connect provider (Keycloak, Microsoft Entra ID, and others). Users in a configured IdP group are mapped to pre-provisioned local accounts. Password login is restricted to the admin break-glass account when SSO is enabled.

Configuration

OIDC is configured in config.json. There is no admin UI for these settings. Restart Anglerphish after changes.

{
  "oidc": {
    "enabled": true,
    "issuer": "https://keycloak.example.com/realms/your-realm",
    "client_id": "anglerphish-admin",
    "redirect_url": "https://admin.example.com:3333/auth/oidc/callback",
    "required_group": "anglerphish-admins",
    "groups_claim": "groups",
    "username_from_email": "local_part",
    "allow_unverified_email": false
  }
}

allow_unverified_email defaults to false, requiring the IdP to assert email_verified: true. Set it to true for providers such as Microsoft Entra ID that do not emit that claim. When no email claim is present, the username is sourced from preferred_username.

Set the client secret via environment variable — do not commit it to config:

export GOPHISH_OIDC_CLIENT_SECRET="your-client-secret"

Keycloak Setup

  1. Create a confidential OIDC client with the standard authorization code flow.
  2. Add redirect URI: https://<admin-host>/auth/oidc/callback — must match redirect_url exactly.
  3. Add a group mapper so the ID token or UserInfo includes a groups claim (array of group names).
  4. Create a realm group (e.g. anglerphish-admins) and assign authorized users.
  5. Set required_group to match the group name Keycloak sends — leading / is normalized automatically.
  6. Pre-create matching local users in the Anglerphish Users page before first SSO login. With username_from_email: "local_part", email firstlast@example.com maps to local username firstlast. The identity provider must include a verified email claim (email_verified: true) for SSO login to succeed.
  7. Provision SSO users with password_change_required disabled — SSO sessions skip the forced password-reset redirect if misconfigured.

Microsoft Entra ID Setup

  1. Register an application (App registrations → New registration) with a Web redirect URI of https://<admin-host>/auth/oidc/callback.
  2. Note the Application (client) ID and Directory (tenant) ID from the Overview page.
  3. Under Certificates & secrets, create a client secret and set it via GOPHISH_OIDC_CLIENT_SECRET.
  4. Under App roles, create a role (e.g. value anglerphish-admins) and assign users in Enterprise applications → Users and groups. Set groups_claim: "roles" and required_group to the role value.
  5. Set issuer to https://login.microsoftonline.com/<tenant-id>/v2.0 and allow_unverified_email: true — Entra ID does not emit the email_verified claim.
  6. Pre-create matching local users. The address comes from the email claim, falling back to preferred_username (the UPN); with username_from_email: "local_part", jsmith@contoso.com maps to local username jsmith.

Entra ID does not connect inbound to the admin console — the callback is delivered by the user's browser. Only the server's outbound access to login.microsoftonline.com (and graph.microsoft.com) is required; allow-list by hostname, not IP.

Behaviour

  • When OIDC is enabled, non-admin users must use Sign in with SSO on the login page.
  • The admin account remains available for break-glass password login.
  • API key authentication is unchanged.
  • SSO login endpoints share the same per-IP rate limit as POST /login (default 5 requests per minute).
  • If OIDC provider discovery fails during a login attempt, Anglerphish retries on the next attempt without requiring a restart.
