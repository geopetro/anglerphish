Landing Pages MFA Extension

MFA simulation adds a second verification step to landing pages. After users submit credentials, they receive an SMS with a verification code and must enter it to proceed.

Additional Page Parameters (MFA):

The following parameters can be included when creating or updating a landing page:

Parameter Type Description
enable_mfabooleanEnable MFA simulation for this landing page
mfa_sms_profile_idintegerID of the SMS profile to use for sending verification codes
mfa_fromstringOverride sender ID for MFA SMS (optional, uses profile default if empty)
mfa_messagestringSMS message template. Use {{.Code}} for the code. Default: "Your verification code is: {{.Code}}"
mfa_code_lengthintegerLength of verification code (4, 6, or 8). Default: 6
mfa_code_typestringCode type: "numeric", "alpha", or "alphanumeric". Default: "numeric"
mfa_inject_pagebooleanIf true, shows built-in MFA verification page. If false, you handle MFA in your landing page HTML. Default: true
mfa_page_htmlstringCustom HTML for MFA verification page (only used if mfa_inject_page is true). If empty, uses default template.
POST /api/pages/

Creates a landing page with MFA enabled. [Show Example]

Request Body:
{
  "name": "MFA Login Page",
  "html": "<html>...</html>",
  "capture_credentials": true,
  "capture_passwords": true,
  "redirect_url": "https://example.com",
  "enable_mfa": true,
  "mfa_sms_profile_id": 1,
  "mfa_from": "MyBank",
  "mfa_message": "Your security code is: {{.Code}}",
  "mfa_code_length": 6,
  "mfa_code_type": "numeric",
  "mfa_inject_page": true
}

Response: 201 Created
{
  "id": 1,
  "name": "MFA Login Page",
  ...
}
GET /api/pages/mfa_template

Returns the default MFA verification page HTML template. Use this to customize the MFA page. [Show Example]

Response: 200 OK
{
  "success": true,
  "message": "Default MFA template",
  "data": "<!DOCTYPE html>\n<html>\n<head>...</head>\n<body>...</body>\n</html>"
}

Template Variables:
- {{if .Error}}...{{end}} - Shows error on failed verification
- Form must POST "mfa_code" field

MFA Events in Campaign Results:

When MFA is enabled, the following additional events are tracked:

  • MFA Code Sent - Code was generated and sent via SMS
  • MFA Code Verified - User entered correct verification code
  • MFA Code Failed - User entered incorrect code

Manage admin SSO (OIDC) settings. See the Admin SSO (OIDC) tab for how SSO works.

  • All endpoints require the Modify System permission. Other users get 403.
  • Changes apply immediately, with no restart.
  • The client secret is never returned. secret_set reports whether one is stored.
  • Errors return {"success": false, "message": "..."}.

Database Encryption

Encrypt sensitive data in the database. Manage it in Settings → DB Encryption.

Keep a copy of your key. Without it, encrypted data can't be recovered.

What Gets Encrypted

  • SMTP, SMS and IMAP passwords
  • Data submitted by targets
  • The SSO client secret

Turn It On

  • Generate in Anglerphish
  • Use your own key
  1. Click Generate key and save the key.
  2. Paste it back to confirm. Encryption is on.
  3. Add the key to your environment as ANGLERPHISH_ENCRYPTION_KEY, so it survives a restart.
  1. Create a key:
    Linux / macOSopenssl rand -base64 32 | tr '+/' '-_'
    Windows (PowerShell)$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); [Convert]::ToBase64String($b).Replace('+','-').Replace('/','_')

    The key is 44 characters. Hex keys don't work.

  2. Set it as ANGLERPHISH_ENCRYPTION_KEY in your environment.
  3. Restart Anglerphish. Encryption is on.
Only new data is encrypted at first. Click Encrypt existing data to encrypt the rest.

If it's locked

A red Encryption locked badge means Anglerphish started without the right key. Profiles with encrypted passwords can't send until you fix it.

You have the keyPaste it into Unlock. Then fix the environment variable.
The key is lostClick Discard encrypted data. Encrypted data is deleted, so re-enter your passwords and the SSO secret.

Turn it off

  1. Click Disable encryption.
  2. Remove ANGLERPHISH_ENCRYPTION_KEY from your environment. Otherwise encryption turns back on at the next restart.

Change the key

  1. With the old key still set, click Disable encryption.
  2. Set the new key and restart.
  3. Click Encrypt existing data.

Starting with a new key while data is still encrypted with the old one locks Anglerphish.

Setting the key on a server

Keep the key out of config.json and the application folder. Replace the paths below with your own.

  • systemd file
  • systemd credential
  • Docker secrets
  • Vault Agent 
sudo mkdir -p /etc/anglerphish
echo "ANGLERPHISH_ENCRYPTION_KEY=your-key" | sudo tee /etc/anglerphish/secrets.env
sudo chmod 600 /etc/anglerphish/secrets.env
sudo chown root:root /etc/anglerphish/secrets.env

# /etc/systemd/system/anglerphish.service
[Service]
EnvironmentFile=/etc/anglerphish/secrets.env
ExecStart=/opt/anglerphish/anglerphish
# /etc/systemd/system/anglerphish.service
[Service]
LoadCredential=encryption_key:/etc/anglerphish/encryption_key
ExecStart=/bin/sh -c 'ANGLERPHISH_ENCRYPTION_KEY="$$(cat "%d/encryption_key")" exec /opt/anglerphish/anglerphish'
# docker-compose.yml
services:
  anglerphish:
    image: your-anglerphish-image
    secrets:
      - anglerphish_encryption_key
    entrypoint: ["/bin/sh", "-c", "ANGLERPHISH_ENCRYPTION_KEY=\"$$(cat /run/secrets/anglerphish_encryption_key)\" exec ./anglerphish"]

secrets:
  anglerphish_encryption_key:
    file: ./anglerphish_encryption_key.txt

Vault Agent writes an environment file. Load it with EnvironmentFile= as in the first example.

# vault-agent.hcl
template {
  contents    = "ANGLERPHISH_ENCRYPTION_KEY={{ with secret \"secret/data/anglerphish\" }}{{ .Data.data.encryption_key }}{{ end }}\n"
  destination = "/etc/anglerphish/secrets.env"
  perms       = "0600"
}

If the admin and phishing servers run as separate processes, always set the key in the environment.

Admin SSO (OIDC)

Let users sign in to Anglerphish with your identity provider. Set it up in Settings → SSO, and changes apply right away.

While SSO is on, only the admin account can sign in with a password. Keep that password: it's your way back in if SSO breaks.

How It Works

Users sign in at your provider. Anglerphish lets them in if they are in the Required group and a user with the same name exists in User Management (jane.doe@example.com signs in as jane.doe). Accounts are not created automatically.

Set Up Your Provider

  • Microsoft Entra ID
  • Keycloak
  • Okta
  • Generic OIDC
  1. App registrations → New registration. Add a Web redirect URI: the Redirect URL from Settings → SSO.
  2. Copy the Application (client) ID and Directory (tenant) ID.
  3. Certificates & secrets: create a client secret and copy its Value.
  4. Token configuration → Add groups claim → Security groups.

Required groupThe group's Object ID (Groups → your group → Overview)
Groups claimLeave empty
Allow unverified emailOn (Entra doesn't send email_verified)

Users in more than 200 groups? Use an app role instead: set Required group to the role's value and Groups claim to roles.

  1. Clients → Create client (OpenID Connect) with Client authentication on.
  2. Valid redirect URIs: the Redirect URL from Settings → SSO.
  3. Copy the secret from the Credentials tab.
  4. Add a Group Membership mapper named groups to the client's dedicated scope, with Add to ID token on.
Issuer URLhttps://<host>/realms/<realm>
Required groupThe group name, e.g. anglerphish-admins
Groups claimLeave empty
Allow unverified emailOff (mark users' emails as verified)
  1. Applications → Create App Integration: OIDC, Web Application.
  2. Sign-in redirect URIs: the Redirect URL from Settings → SSO. Copy the Client ID and secret.
  3. Security → API → Authorization Servers → default → Claims: add a groups claim (ID token, type Groups, filter Matches regex .*).
  4. Assign your group to the app.
Issuer URLhttps://<your-org>.okta.com/oauth2/default
Required groupThe group name, e.g. anglerphish-admins
Groups claimLeave empty
Allow unverified emailOff

No default authorization server? Use https://<your-org>.okta.com as the Issuer URL and set the groups claim on the app's Sign On tab instead.

Any OpenID Connect provider works (Authentik, Google Workspace, Auth0, ADFS…) if it:

  • publishes <issuer>/.well-known/openid-configuration (what Test connection checks),
  • supports the authorization code flow with a client secret,
  • sends the user's email and groups in the ID token or UserInfo.
Issuer URLFrom your provider's OIDC settings
Required groupThe group exactly as the provider sends it
Groups claimLeave empty if the claim is called groups
Allow unverified emailOnly if the provider never sends email_verified

Finish in Settings → SSO

  1. Create the users in User Management (e.g. jane.doe).
  2. Pick the provider, fill in the fields, then click Test connection.
  3. Tick Enable SSO, save, and try it in a private window.

If sign-in fails

“Access denied” on the login page after signing inCheck that the user is in the Required group and exists in User Management. For Entra, turn on Allow unverified email.
Error on the provider’s page mentioning the redirect URICopy the Redirect URL from Settings → SSO and register exactly that at your provider.
SSO shows “Unavailable” in Settings → SSOThe encryption key isn’t loaded, so the client secret can’t be read. Unlock it in Settings → DB Encryption.
